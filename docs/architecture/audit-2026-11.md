# Ember technical debt audit, November 2026

Audited commit: `89c9fa9` (`v2/next`), 2026-11-20. Read-only: no product code was changed for this report.

Scope: `src/Ember.Core`, `src/Ember.Api`, `src/Ember.Bot`, migrations, `tests/`, `web/`, `mobile/android`, `ops/`, `docker*`, `.github/workflows`.

How to read the findings:

- **bug**: traced from a real entry point (UI action, live endpoint, Quartz job) with the data that triggers it, down to the failing line. Traced by reading the code, not reproduced.
- **unconfirmed**: looks wrong, but there is no complete trace, or the intent is unknown.
- **debt**: works today, costs time or safety as Ember grows.
- Severity is about growth and maintainability: **high** blocks safe change, **med** causes drift or slows every change in that area, **low** is a local cost.

## 1. Summary for Nico

Ember's foundations are sound. Core depends on nothing Discord or ASP.NET specific, the schema is configured in one place, every user table cascades on account deletion, migrations are tested against Postgres, the API tests are real black-box HTTP tests, and the web app has no upward imports, no `any` and typed i18n keys. Nothing needs an emergency fix. These are the debts that will hurt most as Ember grows:

1. **HabitService does almost everything.** It is one class split over 13 files: 3,220 lines, about 160 public methods and at least nine jobs (consent, habits, check-ins, streak rules, reminders, accounts, merge and import, journal, settings). 54 files in the API and the bot use it. Every new feature lands there, and a new developer can't tell where anything lives. The pure rules (streaks, days, stats) sit as static methods on this database-bound service, and their optional parameters quietly change the result, so callers already compute the same numbers in different ways.
2. **The same rules exist in up to four places.** Habit rules live in Core, again inside bot jobs, again as API validators, again in TypeScript for the no-account mode, and partly again in the Android widget. Shared JSON fixtures keep days and stats in sync between C# and TypeScript, but not weekly summaries, pause, limits or the default weekly target (`WeeklyTarget ?? 3` is written 8 times). That drift already produced one real bug (routine reminders, see 3.3).
3. **What counts as "your data" is a hand-kept list, six times over.** Withdrawing consent, export, import, merge and the stale-account cleanup each list the health tables themselves. A new table that one list misses stays stored after withdrawal or is lost on merge, and nothing fails. For a health-adjacent app that is the riskiest kind of drift.
4. **Security rules are opt-in.** An API endpoint is anonymous unless its author remembers `.RequireAuthorization()`. There are 8 token kinds with 4 storage styles. `/privacy delete` in Discord deletes an email account with a password and 2FA without asking for either, while the web asks for the password.
5. **The safety nets have holes.** There is no `.editorconfig`, no analyzer or format gate and no ESLint. The Android tests and the whole ops suite (including the database grant tests) never run in CI. The bot and Core tests run on SQLite while production runs Postgres, so a refactor can pass every bot test and still break production. The API suite runs all ~480 tests one after another, each with a fresh database.
6. **The bot has no layers.** Discord modules, jobs and services all call each other's static methods. About 30 button id formats are built as inline strings, with the producer and the parser in different files, so a typo silently kills a button.
7. **A few files are too big to change safely.** `web/src/pages/settings.tsx` (1,591 lines, about 20 `useState`, 25 sections, one change pattern pasted five times), `mobile/android/.../TodayWidget.java` (915 lines: storage, HTTP, rendering and validation in one class) and `src/Ember.Bot/Jobs/ReminderDispatchJob.cs` (595 lines with rules that belong in Core).

What I recommend *not* doing: no MediatR or CQRS, no repository interfaces, no DTO folder, no move to React context, no Glance rewrite of the widget, no separate worker host, no feature-folder namespace churn across 40 files in one go. None of those pay for themselves at Ember's size.

## 2. Current architecture

### 2.1 Processes and data flow

```
                Discord gateway                       Browser / Android WebView
                      |                                         |
              +---------------+                         +---------------+
              |   Ember.Bot   |                         |   Ember.Api   |  serves web/dist too
              | 20 modules    |                         | 18 *Endpoints |
              | 7 Quartz jobs |                         | 94 routes     |
              | migrates DB   |                         | 3 CLI modes   |
              +-------+-------+                         +-------+-------+
                      |   HabitService (13 partials), FiresideService, ...   |
                      +-----------------> Ember.Core <------------------------+
                                              |
                                        EmberDbContext  ---->  PostgreSQL (emberdb)
                                                                  ^
   lookout-sender (Ember.Api binary, --lookout-sender) -----------+  outbox -> Lookout
   ember-ops (ops/, raw Npgsql, read-only column grants) ----------+  + own emberops DB
```

- **Bot** (`src/Ember.Bot`): one generic host (`AppHost.cs:28-148`). On start it migrates (`AppHost.cs:160-163`), re-arms reminders (`:165-177`) and starts Discord plus 7 Quartz jobs (`:64-107`): reminder dispatch every minute, Discord ask, Fireside notify, weekly summary and missed-day reflection every 15 minutes, account cleanup and health-data deletion daily. The bot sends web push too, so it is the scheduler for every channel, not only a Discord adapter.
- **API** (`src/Ember.Api`, 39 files in the project root plus `Email/`, about 5,300 lines): `Program.cs` dispatches on args (`--healthcheck`, three CLIs, `--lookout-sender`, else web app). Pipeline in `ApiApp.Build`, with 5 custom middlewares. A `signedIn` group requires auth; 5 maps sit on the bare `api` group with auth set per endpoint (`ApiApp.cs:196-200`). Handlers validate into a `Dictionary<string,string[]>`, call Core, and map to DTOs nested in the endpoint class.
- **Core** (`src/Ember.Core`): 24 models, one `EmberDbContext : IdentityUserContext<User, Guid>` with all mapping fluent in `OnModelCreating` (`EmberDbContext.cs:39-382`), services (HabitService, FiresideService, DeletionLedger, static ExportBuilder and WeeklySummaryService), localization. References only Identity.EntityFrameworkCore and Npgsql.
- **Database**: about 27 tables, 31 migrations. Only the bot migrates. Both bot and API write the same tables with no concurrency tokens.

### 2.2 Web app (`web/`)

```
pages/ (30 routes) -> components/<feature>/ + components/ui/ -> lib/
                                                                  |
         useQuery/useMutation inline (54 calls in 33 files) -> api-client.ts -> http.ts
                                                                  |            |
                                                     Http.local ? LocalBackend (IndexedDB, regex routes, rules.ts)
                                                                  : fetch /api (+ offline cache, offline queue)
```

- `lib/services.ts:20-64` builds every singleton and wires them by property assignment; 76 files import it.
- The no-account mode fakes the HTTP layer (`http.ts:270-273` to `local/backend.ts:407-450`), so screens don't know which backend they talk to. That seam is good.
- `models.ts` is written by hand from `docs/contracts/api-v1.md`; there is no OpenAPI.
- Rules parity: `docs/contracts/fixtures/rules-v1.json` (15 cases) and `letgo-v1.json`, checked by `tests/Ember.Tests/RulesFixtureTests.cs` and `web/src/lib/local/rules-parity.test.ts`. They cover days, stats, dayStats and routinePending only.
- 106 unit test files (about 19,500 lines), 29 Playwright specs, no snapshot tests.

### 2.3 Android (`mobile/android`)

Capacitor 8 template, AGP 8.13, Java 21, no Kotlin plugin. 11 Java files in one package: `MainActivity`, `TodayWidget` (915 lines), `MomentWidget`, pure helpers (`WidgetPlan`, `WidgetPalette`, `ScreenTime`, `AppLanguage`), `WidgetKey` (AndroidKeyStore AES-GCM), plugins (`EmberWidgetPlugin`, `BackupFilePlugin`, beta `EmberUpdaterPlugin`). 4 JVM test files.

### 2.4 Ops, Docker, CI

- `ops/` is a separate deployable (Lookout provider `ember-ops`) with its own slnx, Dockerfile, compose file, systemd timer and deploy branch `v2/next-ops`. It shares no code with Ember; only its test host references `Ember.Core` to apply the real migrations, which is the right way to keep one schema.
- Docker: multi-stage `api.Dockerfile` and `bot.Dockerfile`, both non-root. Compose runs `ember`, `api` (profile) and `lookout-sender` (profile, the only hardened one).
- CI (`.github/workflows/ci.yml`): .NET restore, vulnerable-package check, build, test of `Ember.slnx`; web unit tests and two builds; Playwright in 3 shards. Dependabot covers NuGet and Actions.

Layer rules:

1. Rules are pure: no EF, no `TimeProvider` (today and now come in as arguments), no optional parameters that change the result.
2. Core is the consent gate for every health-data write. Callers may pre-check for UX only.
3. Expected outcomes (limit reached, consent missing, not found) are result enums. Exceptions are for bugs and bad input that callers should have validated.
4. Every query lives in Core. State that both bot and API write is updated with `ExecuteUpdate` or compare-and-set, not tracked read-modify-write.
5. No new `ulong` overloads.
6. Core references no Discord, ASP.NET Core hosting or Quartz package.

Naming (Microsoft .NET guidelines): no `Helper` suffix (`TimezoneHelper` becomes `TimeZones`), static classes that compute are not called `Service` (`WeeklySummaryService` becomes `WeeklySummary`), `GetUserTzAsync` becomes `GetTimeZoneAsync`. Rename only in the slice that touches the file. Keep the namespace `Ember.Core.Services` for services so 40 consumer files don't change their usings; new folders get matching namespaces (`Ember.Core.Rules`, `Ember.Core.Privacy`).

  Auth/        AuthEndpoints, AuthSessions, EmberSignInManager, EmberUserValidator, TwoFactorEndpoints, DiscordEndpoints, PasswordChecks

Rules:

- An endpoint parses the request, calls Core and maps the result. It doesn't touch `EmberDbContext`; `AuthSessions` is the one API-owned exception.
- Endpoints never reference other endpoints. Shared validation lives in a feature-neutral class or in Core constants.
- Only `Problems` builds problem responses.
- Every route group declares its auth; an inventory test enforces it.
- Request and response records stay nested in their `*Endpoints` class: they are that feature's wire contract.
- Keep the hand-rolled validation dictionaries; they are consistent. No MediatR, FluentValidation, controllers or options rewrite.
- `*Endpoints` static classes with `Map*` on `RouteGroupBuilder` already follow Microsoft's minimal API guidance; keep that. One public type per file.

### 4.3 Ember.Bot

```
src/Ember.Bot/
  Hosting/        AppHost, Program, Quartz registration
  Discord/
    Gateway/        BotService, DiscordDmSender, notifiers
    Interactions/   <Feature>/ modules
    Messages/       static builders: reminder DM, consent prompt, ask, Fireside notice, DM retry
    Formatting/     HabitText
    CustomIds/      one static class per feature
  Notifications/  IReminderChannel, DiscordDmReminderChannel, WebPushReminderChannel, WebPushSender, ReminderRetries
  Jobs/           orchestration only
  Resources/
```

Rules:

- Modules and jobs are leaves: nothing references them.
- `Notifications` may use `Discord/Messages` and Core. `Messages` and `Formatting` use only Core and `BotTexts`.
- Every rule about time, eligibility or completion lives in Core as a pure function.
- Custom ids: `{feature}:{action}[:{arg}...]`, args are int ids, `yyyyMMdd` dates or unix seconds; the owner's Discord id only for account-level actions. One `const` handler pattern and one builder per id. Ids already in use never change.
- The scheduler stays in the bot process (see D10). A failed Discord login must not stop the jobs.
- Folder moves happen inside the slices that touch the files; Discord.Net finds modules across the assembly, so namespace moves are safe.

### 4.4 Data layer

- Fluent configuration only, one block per entity. Split into `IEntityTypeConfiguration<T>` files only once `EmberDbContext.cs` passes about 600 lines (it has 383).
- Migrations: always `dotnet ef migrations add`. Expand and contract across releases; a migration never backfills and drops its source in one go. Deploy order: bot migrates, then API. Data steps are SQL inside the migration, with a test that migrates to N-1, seeds, then goes to N (the existing pattern).
- An index needs a named query. Filtered indexes for sparse columns. No indexes ahead of volume.
- Every new migration is a one-way door on production and needs Nico's go, as today.

### 4.5 Web

```
web/src/
  pages/              route shells, under ~300 lines each
  components/<feature>/, components/ui/
  hooks/              query and mutation hooks: use-today.ts, use-me-patch.ts, ...
  lib/                no React (store.ts excepted); query-keys.ts; local/, native/, journal/, ...
  test/               all test helpers (from lib/test-support.ts, src/test-utils.tsx, components/journal/fake-journal.tsx)
```

Import rules (enforced by ESLint): `pages` may use `components`, `hooks`, `lib`; `components` may use `hooks`, `lib`, `ui`; `hooks` may use `lib`; `lib` uses only `lib`; `components/ui` uses nothing app-specific; `lib/local/*` is imported only by `services.ts` and the mode switch.

- One source of truth for rules: `docs/contracts/fixtures/*.json`, asserted by both C# and TS, including limits.
- Naming: kebab-case files (already the case), one exported component per file, `use-*.ts` for hooks.
- ESLint: `typescript-eslint` `recommendedTypeChecked` plus `stylisticTypeChecked`, `no-floating-promises` on, `eslint-plugin-react-hooks` recommended (errors), react jsx-runtime, `import/no-restricted-paths` or `eslint-plugin-boundaries` for the import rules, `@tanstack/eslint-plugin-query`, `eslint-config-prettier`. Move to `strictTypeChecked` one rule family at a time.
- tsconfig: add `noUncheckedIndexedAccess`; consider `exactOptionalPropertyTypes` later.
- Keep `services.ts` singletons and the HTTP-fake local backend. Generated models from OpenAPI would be right long term but need server work first; the fixtures give more per hour.

### 4.6 Android

- New Android code in Kotlin. A Java file moves to Kotlin when its area is touched, after its prerequisites.
- While Java callers remain, use `object` with `const val`, `@JvmField` and `@JvmStatic`; avoid `internal` on members Java calls (the names get mangled).
- Layout, still one module: `widget/` (store, check-in client, views, receivers), `plugin/`, `MainActivity`.
- No Glance (the widget already uses sized `RemoteViews`; a Compose runtime and a 900-line rewrite don't pay). No WorkManager now (the 8 s `goAsync` plus JS replay fits the "short async work" guidance).
- Android lint with a baseline and JVM tests in CI.

### 4.7 Ops, Docker, CI

- Ops stays a separate deployable with least-privilege SQL, but builds and tests in the one solution and the one CI.
- Every container: non-root, `read_only` where it can, `cap_drop: [ALL]`, `no-new-privileges`, file secrets.
- CI: format, analyzers, lint and every test suite are required checks; actions pinned by SHA; `permissions: contents: read`; one concurrency group per ref.

### What the behavior baseline must cover first

The baseline team (`v2/next-baseline`) should make sure these exist before Wave 2:

1. Postgres runs for bot and Core paths: reminder dispatch (due, overdue, paused, retry, DM pause counter), check-in and low-day double-tap races.
2. Transactional services on Postgres: merge, import, journal turn-off, Fireside transactions. A failure half-way leaves no partial rows.
3. Health-data withdrawal empties every health table; export lists every exported table.
4. Weekly summary idempotency: a second run on the same Sunday sends no second recap.
5. API JSON shape per resource (`GET /api/habits`, `/habits/{id}`, `/habits/{id}/days`, `/api/me`): the web client depends on the wire format, so the exact shape is the contract.
6. Bot routing: every emitted custom id resolves to a handler; handlers reject another user's ids and malformed ids for each button family.
7. Job wiring: each job is registered with its cron and does not run concurrently.
8. Android: JVM tests for widget snapshot validation, pending merge and `takePending`; `EmberUpdaterPlugin.matches`.
